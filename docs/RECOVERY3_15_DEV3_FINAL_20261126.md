## 2. RAM e Informe Maestro
`include/cielo_report315.h` incorpora un escritor de fragmentos con reserva de 4096 bytes frente a los 28000 anteriores. Las secciones grandes ya generadas por auxiliares se envían directamente sin copiarlas al búfer de fragmentos. `cieloTrendJson` y `appendHealth314` emiten directamente al escritor; se suprime la reserva anterior de 9000 para el historial. El búfer no es un límite para toda la RAM ni se ha medido el heap en el dispositivo. El writer detecta concatenación fallida, fragmento vacío y fallo indicado por el sink. El servidor tiene un límite cooperativo de 10 s entre envíos; una escritura TCP bloqueante puede excederlo. No se afirma entrega extremo a extremo a partir de los contadores del ATOM.

Se mantiene el esquema `iwagumi-cielo-96-diagnostico-v3` y se añaden `report_id`, `request_nonce`, `report_transport`, `report_crc32`, `report_complete`. El epoch y la fecha inicial comparten una captura del reloj. El navegador usa nonce aleatorio de 128 bits, no-cache, abort a 15 s, comprueba el esquema, identidad, CRC32 sobre bytes UTF-8 del prefijo y trailer completo antes de crear el archivo. La CRC32 no autentica al servidor ni sustituye TLS. El cuerpo original se conserva sin reserializar. Nombre único por informe normal; la ruta share conserva el nombre compatible anterior y la supresión de datos sensibles. Direct HTTP downloads no tienen la comprobación del navegador salvo que la apliquen sus clientes.

Se consultó el código de Arduino-ESP32 2.0.17 para confirmar `WebServer::send` con cuerpo vacío y `CONTENT_LENGTH_UNKNOWN`, `sendContent` y terminación de chunks. Referencias:
- https://github.com/espressif/arduino-esp32/blob/2.0.17/libraries/WebServer/src/WebServer.cpp
- https://github.com/espressif/arduino-esp32/blob/2.0.17/cores/esp32/WString.h
Limitaciones: `sendContent` no expone el resultado exacto de cada escritura. El CRC y trailer del cliente detectan incoherencia o truncamiento de transporte, no todos los posibles fallos semánticos de los auxiliares String heredados. El servidor HTTPS inactivo conserva el proxy original, que no decodifica el chunking de su backend: si se reactivase HTTPS, adaptar el proxy y ensayar el flujo. No se activa ni altera en DEV3.

## 3. Historial LittleFS independiente
`include/cielo_history315.h`: dos archivos `/cielo-lfs/cielo_hist315_a.bin` y `..._b.bin`, formato v1, 864 bytes por archivo, 1728 bytes de payload total (el uso físico incluye metadatos y bloques). Magic/version, generación, epoch, número de días, CRC32 y validación de calendario/orden. No se sobrescribe el slot válido más reciente. Escritura del inactivo con fsync, cierre, relectura y comprobación CRC. Si ambas copias son inválidas se conserva el contenido y se bloquean nuevas escrituras. Si existe un archivo desconocido o un error de lectura y hay una copia válida, se restaura esta última sin permitir nuevas escrituras. No hay borrado ni recuperación destructiva. CRC accidental, no firma. El soporte real de fsync, durabilidad y recuperación ante pérdida de energía debe validarse en LittleFS del ATOM; el ensayo POSIX no equivale a ese hardware.

La ventana contiene los últimos 30 días observados, no necesariamente 30 días naturales consecutivos. Se restaura el resumen sin recrear muestras. Los datos nuevos se acumulan con los contadores de este arranque. Días anteriores al último restaurado se rechazan y se contabilizan; no se inventan datos faltantes. El anillo de las últimas 96 muestras sigue en RAM y pertenece a este arranque. El primer checkpoint puede hacerse a partir de 15 minutos de uptime si las condiciones son seguras. Después, al menos 6 horas desde el último checkpoint válido, y quietud de arranque; protección monotónica adicional dentro de un mismo arranque ante salto del reloj. Reintento mínimo 30 min tras fallo o falta de espacio. El margen libre exigido es 65536 bytes. No escribe durante OTA (incluido candidato sin validar), rescate, mantenimiento, laboratorio, cola ocupada, recuperación aislada, interlock PV, retorno CH o watchdog. Por la noche solo es elegible tras OFF GATT aceptado y lejos del siguiente intento OFF. No supone que se guardará exactamente a las 6 h: las condiciones inseguras pueden aplazar indefinidamente. Un corte puede perder datos no guardados. La restauración no demuestra luz óptica ni continuidad de operación durante el corte.
